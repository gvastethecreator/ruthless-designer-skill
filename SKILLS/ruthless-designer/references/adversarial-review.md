# Adversarial Design Review

Use when a redesign, visual critique, or proposed direction risks settling for competent but weak work. Challenge the artifact and the proposed replacement with equal force. Keep this reasoning in working notes unless a review artifact is requested.

## Read Without The Defense Speech

Inspect the interface or supplied reference before its source or designer explanation. Name what actually dominates, what the task requires, and which content or action loses. Treat this as an expert reading, not measured user attention. Examine the task's decision and costly transition as well as the first impression.

Use three levels of inspection:

- Whole surface: primary artifact, attention order, composition, density, reading path, proof, navigation and scroll ownership.
- Relationships: grouping, comparisons, repeated rows, type roles, action rank, state language, distance between a control and its effect.
- Detail: baselines, optical centers, icon family, crop, edge treatment, contrast in state, wrapping and clipping at actual size.

Check a realistic pressure state: uncertainty, interrupted work, long content, unavailable data, or recovery. A beautiful idle frame does not establish a good product.

## Cross-Examine Each Accusation

A material finding needs an observable subject, consequence, cause or labeled hypothesis, exact replacement, and an acceptance condition. Group repeated symptoms by cause. Keep observation, source confirmation, and inference distinct.

Before retaining it, answer: what evidence would make this choice correct? Look for intentional density, a learned control, a brand constraint, domain literacy, or a platform convention. Reject the accusation if those facts defeat it. A familiar font, native scrollbar, grid, card, gradient, or restrained screen is not guilty by category. Conversely, "the design system does this" does not excuse an observed task failure.

Do not report numerical contrast, timing, conversion impact, task speed, or comprehension without matching measurements. Hypotheses can be consequential; they still need a test. Rank by user damage and the requested design goal, not by certainty of tone.

## Name The Dominant Cause

Ask these questions before cosmetic cuts:

- Is the main object subordinate to navigation, summaries, diagnostics, or decoration?
- Must the user infer scope, units, freshness, ownership, consequence, or next action?
- Does grouping match the user's decision, or the application's internal features?
- Do selection, displayed data, status, and available actions stay consistent during transitions?
- Does one repeated primitive or content rule create several apparent defects?
- Is the visual language specific to the artifact, audience, material, or workflow? What real relationship would improve if it changed?

The dominant cause should explain several symptoms when the evidence supports that link. Do not merge unrelated failures to make the story elegant. Preserve mechanisms that already work, even when rebuilding their presentation.

## Make The Alternative Beat The Original

For broad direction work, compare genuinely viable alternatives. A credible small repair is a useful benchmark: a redesign must earn its extra disruption. For greenfield work, compare against a competent conventional solution for the actual brief. Do not invent a bad baseline to make your proposal win.

Describe each serious option in terms of:

- Composition: dominant object, reading path, space allocation, comparison and action zones.
- Visual system: type roles, palette roles, spacing relationships, media or material, and repeated component grammar.
- Behavior: how action, feedback, uncertainty, and recovery work under pressure.
- Gain and cost: what becomes clearer or more specific; what familiarity, density, content, or implementation simplicity is lost.
- Discriminator: the observable result that would make this option win or lose.

Use a rough layout, existing component sketch, or simple wireframe when prose cannot distinguish spatial options. Do not build several full products just to compare them. If all options share the same boxes and differ only in palette, they are one option.

Select the direction with the strongest task and visual argument. Define one visible signature caused by the product, not a novelty quota. A clear comparison model or artifact-led workbench can be distinctive through its structure. Keep standard controls understandable.

## Attack Your Own Replacement

Before accepting the result, inspect it without the direction card. Try to find a stronger objection than the one made against the original:

| Challenge | Reject the replacement when |
|---|---|
| Priority | The same wrong object dominates under a new palette |
| Specificity | Swapping logo and nouns preserves every major decision |
| Information | Removing clutter also removed decision evidence, scope, status, or recovery |
| Pressure | The main path looks good but realistic content or a costly state breaks it |
| Familiarity | Novel controls make frequent work harder without a compensating benefit |
| Craft | Typography, spacing, crop, icons, or state contrast contradict the chosen direction |
| Honesty | Mock claims, decorative telemetry, or fake assets are presented as product evidence |
| Proof | Different data, viewport, theme, or loading state explains the apparent improvement |

Compare before/after as better, flat, worse, or inconclusive on the changed goals. Name both gain and regression; do not average away a broken task with visual polish. A claim can pass only on its own evidence. See [proof.md](proof.md) for production integrity, task effectiveness, and distinctiveness.

If the same cause survives a valid comparison, change the responsible structure instead of escalating decoration. If a promising direction loses useful behavior, repair that regression before accepting it. Do not reset a whole product because proof was missing or one crop was wrong.

## Deliver A Decisive Finding

Weak: "The interface needs better hierarchy and a premium feel."

Useful: "The weekly summary occupies the decision area while unresolved items require another view. Put unresolved items and their evidence in that area, move the summary to supporting context, and keep the existing filters. At the representative viewport, an operator should be able to inspect and act on the selected item without leaving the list. Task-speed improvement remains unmeasured."

Be direct without performing hostility. A precise, defensible cut is more useful than a louder verdict. No quotas, fabricated scores, or invented defects to justify the skill's name.
